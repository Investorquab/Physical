01 / Abstract

From physical observation to programmable consequence

PHYSICAL is a DePIN coordination layer that turns real world infrastructure observations into verifiable cross chain actions. The prototype uses OpenAQ air quality data as its physical data source. A worker retrieves an observation, normalizes it, and commits a structured event to Ethereum Sepolia.

The Attestcoin Protocol provides the verification path required for a Creditcoin smart contract to confirm the source transaction and event before a destination action is allowed. After verification, a coordination rule evaluates the observation. A configured PM2.5 threshold, for example, can trigger a real Creditcoin testnet settlement transaction.

Core principle. PHYSICAL does not create virtual sensor readings. It uses existing infrastructure and makes the resulting cross chain decision traceable.
02 / Problem

Physical data is useful, but isolated

Physical infrastructure produces valuable information about environmental conditions, energy systems, logistics, mobility, and other real world processes. Yet this information is commonly isolated inside provider APIs and dashboards. An API response alone is not sufficient for a destination smart contract to independently confirm what was committed on another chain.

A reliable coordination system needs a connected evidence path: the physical source, normalized payload, source chain commitment, cross chain proof, destination verification, and final action. Without this path, an application may depend on an opaque backend claim.

PHYSICAL addresses this gap by separating data acquisition from cross chain verification and business logic.

03 / Product overview

Built on existing infrastructure, not simulated hardware

The first implementation focuses on air quality because air quality data is measurable, time dependent, geographically meaningful, and available through an existing sensor network. OpenAQ provides measurements and station metadata that PHYSICAL can retrieve without deploying a new hardware network for the prototype.

PHYSICAL is designed around four principles:

  • Use real infrastructure and real observations instead of invented hardware data.
  • Keep source data, transport, verification, and business rules separate.
  • Make Attestcoin essential to the cross chain execution path.
  • Expose evidence so users can inspect the result.

05 / Data layer

Normalizing real observations into stable events

The ingestion worker uses OpenAQ API credentials to retrieve measurements. A source response is converted into a stable internal payload containing the provider, station identity, location metadata, measured parameter, value, unit, observation timestamp, source reference, and payload hash.

Normalization gives the system a consistent representation even when provider responses contain additional fields or presentation specific metadata. Deduplication prevents the same source observation from being committed repeatedly, while persistence connects the provider response to the later source transaction and event reference.

OpenAQ remains the physical data source. PHYSICAL preserves attribution and does not claim that Attestcoin independently establishes the accuracy of the underlying sensor reading.

06 / Source commitment

The source chain records what PHYSICAL intends to verify

The source contract is intentionally narrow. Its responsibility is to receive the normalized observation and emit a structured event. The source chain commitment creates a durable reference that can be independently located and verified later.

The event connects the observation to its source provider, station, measured parameter, value, timestamp, and payload hash. The payload hash binds the application record to the committed event data without requiring the source contract to contain the entire application database.

Physical observation ↓ Normalized payload ↓ SourceEventRegistry ↓ Ethereum Sepolia transaction ↓ Structured source event ↓ Attestcoin verification on Creditcoin

This separation follows the Attestcoin design principle that source contracts should focus on emitting events while destination contracts perform the application specific business logic.

07 / Attestcoin integration

Attestcoin is the verification layer

Attestcoin, formerly known as Universal Smart Contracts, is the core verification layer of PHYSICAL. The oracle worker monitors SourceEventRegistry events and waits until the relevant Ethereum block is eligible for attestation. It then obtains the required Merkle and continuity proofs and submits them to PhysicalASC on Creditcoin.

Source event on Ethereum Sepolia ↓ Source block attestation ↓ Merkle proof and continuity proof ↓ PhysicalASC on Creditcoin ↓ Native Attestcoin verifier precompile ↓ Validated source transaction and event ↓ Verified physical event

PhysicalASC validates the source transaction context, decodes the verified transaction data, checks the expected event, applies replay protection, and emits a Creditcoin side verified event. An unverified API response cannot directly authorize the destination action.

The native verifier precompile used by the destination contract is:

0x0000000000000000000000000000000000000FD2

Without Attestcoin, PHYSICAL would have no verifiable cross chain mechanism connecting the Ethereum source commitment to the Creditcoin coordination contract.

08 / Coordination

Verified data drives deterministic rules

A coordination rule defines the condition under which a verified observation should produce an action. A rule can identify the provider, station, measurement parameter, comparison operator, threshold, and action type.

If a verified PM2.5 observation is greater than the configured threshold, create a settlement action on Creditcoin.

The rule engine only evaluates observations that have passed Attestcoin verification. When a condition is satisfied, PhysicalSettlement records the action and produces a real Creditcoin CC3 testnet transaction.

09 / Settlement

A physical condition can trigger a real testnet transaction

When a verified observation satisfies a coordination rule, PHYSICAL calls PhysicalSettlement. The settlement contract records the action and produces a real Creditcoin CC3 testnet transaction.

The frontend displays the observation, source commitment, verification evidence, rule result, and settlement reference. This gives the user a complete path from the original physical observation to the final destination transaction.

10 / Security model

Clear boundaries between data, proof, and execution

Source data trust

OpenAQ and the underlying sensor operators are responsible for producing the physical measurement. PHYSICAL does not claim that Attestcoin proves the sensor is honest or that a measurement is free from physical world error.

Cross chain trust

Attestcoin verifies that the source transaction and event are included in the source chain according to the supplied proof and attestation process. This creates an independently verifiable connection between the source commitment and the Creditcoin application.

Destination execution

Creditcoin contracts evaluate the verified event and execute deterministic rules. The frontend is not the trust anchor. Expected source context, event validation, replay protection, and separation of source data from destination state reduce the risk of an incorrect or repeated action.

11 / Operational flow

One observation, one evidence trail

  1. The worker retrieves a real OpenAQ measurement.
  2. The observation is normalized and stored.
  3. SourceEventRegistry commits the observation on Ethereum Sepolia.
  4. The source transaction becomes eligible for attestation.
  5. The worker obtains Merkle and continuity proofs.
  6. PhysicalASC submits the proof to the native verifier.
  7. The verified event becomes available to the coordination layer.
  8. The rule engine evaluates the observation.
  9. PhysicalSettlement records the action and submits the Creditcoin transaction.
  10. The frontend displays the complete evidence path.
12 / DePIN relevance

Using physical infrastructure to drive programmable coordination

PHYSICAL fits the DePIN track by using existing physical sensor infrastructure as the input to a programmable coordination system. The physical data is not decorative. It drives the cross chain decision and can trigger a settlement action on Creditcoin.

The architecture can be extended beyond air quality to other sensor networks that expose verifiable observations, including environmental monitoring, energy telemetry, mobility systems, logistics infrastructure, and industrial measurements.

13 / Limitations

A focused testnet prototype

The current implementation uses a limited rule configuration, a controlled set of supported measurement flows, and a single VPS deployment. It is not presented as a production ready decentralized sensor network.

The system proves source chain commitment and cross chain verification. It does not replace source data quality controls, sensor calibration, provider accountability, or physical inspection.

14 / Roadmap

From prototype to broader infrastructure

  • Expand rule creation and management.
  • Add broader measurement types and providers.
  • Introduce durable retry queues and operational monitoring.
  • Add automated integration and negative path tests.
  • Support more physical data providers and sensor networks.
  • Add stronger permission and audit controls.
  • Improve production deployment resilience.
15 / Conclusion

Making physical infrastructure actionable across chains

PHYSICAL demonstrates how existing physical infrastructure data can become a verifiable on chain consequence. A real OpenAQ observation is normalized, committed to Ethereum, verified on Creditcoin through Attestcoin, evaluated by a deterministic rule, and used to trigger a real testnet settlement.

The contribution is not another dashboard that displays an API response. It is an evidence path connecting a physical observation to a programmable action across chains, with clear boundaries between source data, cryptographic verification, and destination execution.
