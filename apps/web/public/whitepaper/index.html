01 / Abstract

From physical observation to programmable consequence

PHYSICAL is a DePIN coordination layer that turns real world infrastructure observations into verifiable cross chain actions. The prototype uses OpenAQ air quality data as its physical data source. A worker retrieves an observation, normalizes it, and commits a structured event to Ethereum Sepolia.

The Attestcoin Protocol provides the verification path required for a Creditcoin smart contract to confirm the source transaction and event before a destination action is allowed. After verification, a coordination rule evaluates the observation. A configured PM2.5 threshold, for example, can trigger a real Creditcoin testnet settlement transaction.

Core principle: PHYSICAL does not create virtual sensor readings. It uses existing infrastructure and makes the resulting cross chain decision traceable.
02 / Problem

Physical data is useful, but isolated

Physical infrastructure produces valuable data, but that data is often separated from programmable financial and coordination systems. An API response alone is not sufficient for a destination smart contract to independently confirm what was committed on another chain.

A reliable system needs a complete evidence path: the physical source, normalized payload, source chain commitment, cross chain proof, destination verification, and final action. Without this path, an application may depend on an opaque backend claim.

PHYSICAL addresses this gap by separating data acquisition from cross chain verification and business logic.

03 / Product overview

A practical first implementation

The first implementation focuses on air quality. OpenAQ provides measurements and station metadata from existing sensor networks. PHYSICAL converts a selected observation into a stable event and sends it through a two chain workflow.

Source chainEthereum Sepolia

The application is designed around four principles:

  • Use real infrastructure instead of invented hardware data.
  • Keep source data, transport, verification, and business rules separate.
  • Make Attestcoin essential to the cross chain path.
  • Expose evidence so users can inspect the result.

05 / Data ingestion

Using existing sensor infrastructure

The ingestion worker uses OpenAQ API credentials to retrieve measurements. Each observation is normalized into a stable payload containing the source provider, station identity, location metadata, measured parameter, value, unit, observation timestamp, source reference, and payload hash.

Deduplication prevents the same source observation from being committed repeatedly. Persistence creates an internal record that connects the provider response to the source chain transaction and event reference.

OpenAQ remains the physical data source. PHYSICAL preserves attribution and does not claim that the cross chain proof independently establishes the accuracy of the underlying sensor.

06 / Attestcoin integration

Attestcoin is the verification layer

Attestcoin, formerly known as Universal Smart Contracts, is the core verification layer of PHYSICAL. The source contract is intentionally simple. Its primary responsibility is to emit a structured event that can later be verified on Creditcoin.

The oracle worker monitors source events and waits until the relevant Ethereum block is eligible for attestation. It then obtains the required proof material and submits it to PhysicalASC on Creditcoin.

Real observation ↓ SourceEventRegistry on Ethereum Sepolia ↓ Attestation and proof generation ↓ PhysicalASC on Creditcoin ↓ Native Attestcoin verifier precompile ↓ Verified physical event ↓ Coordination rule and settlement

PhysicalASC validates the source transaction context, decodes the verified transaction data, checks the expected event, applies replay protection, and emits a Creditcoin side verified event. The destination action is not authorized by an unverified API response.

The native verifier precompile used by the destination contract is:

0x0000000000000000000000000000000000000FD2
07 / Coordination

Verified data drives deterministic rules

A coordination rule defines the condition under which a verified observation should produce an action. A rule can identify the provider, station, parameter, comparison operator, threshold, and action type.

If a verified PM2.5 observation is greater than the configured threshold, create a settlement action on Creditcoin.

The rule engine only evaluates observations that have passed Attestcoin verification. When a condition is satisfied, PhysicalSettlement records the action and produces a real Creditcoin CC3 testnet transaction.

08 / Trust and security

Clear boundaries between data and proof

Source data trust

OpenAQ and the underlying sensor operators are responsible for producing the physical measurement. PHYSICAL does not claim that Attestcoin proves the sensor is honest or that a measurement is free from physical world error.

Cross chain trust

Attestcoin verifies that the source transaction and event are included in the source chain according to the supplied proof and attestation process. This creates an independently verifiable connection between the source commitment and the Creditcoin application.

Destination execution

Creditcoin contracts evaluate the verified event and execute deterministic rules. The frontend is not the trust anchor. Replay protection, expected source context, event validation, and separation of source data from destination state reduce the risk of an incorrect or repeated action.

09 / Operational flow

One observation, one evidence trail

  1. The worker retrieves a real OpenAQ measurement.
  2. The observation is normalized and stored.
  3. SourceEventRegistry commits the observation on Ethereum Sepolia.
  4. The source transaction becomes eligible for attestation.
  5. The worker obtains Merkle and continuity proofs.
  6. PhysicalASC submits the proof to the native verifier.
  7. The verified event becomes available to the coordination layer.
  8. The rule engine evaluates the observation.
  9. PhysicalSettlement records the action and submits the Creditcoin transaction.
  10. The frontend displays the complete evidence path.
10 / Limitations

A focused testnet prototype

The current prototype uses a limited rule configuration, a controlled set of supported measurement flows, and a single VPS deployment. It is not presented as a production ready decentralized sensor network.

The system proves source chain commitment and cross chain verification. It does not replace source data quality controls, sensor calibration, provider accountability, or physical inspection.

11 / Roadmap

From prototype to broader infrastructure

  • Expand rule creation and management.
  • Add broader measurement types and providers.
  • Introduce durable retry queues and operational monitoring.
  • Add automated integration and negative path tests.
  • Support more physical data providers and sensor networks.
  • Add stronger permission and audit controls.
  • Improve production deployment resilience.
12 / Conclusion

Making physical infrastructure actionable

PHYSICAL demonstrates how existing physical infrastructure data can become a verifiable on chain consequence. A real OpenAQ observation is normalized, committed to Ethereum, verified on Creditcoin through Attestcoin, evaluated by a deterministic rule, and used to trigger a real testnet settlement.

The contribution is not another dashboard that displays an API response. It is an evidence path connecting a physical observation to a programmable action across chains.
